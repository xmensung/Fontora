# Fontora 功能缺口详解

对照对象：Anyway.Fonts（https://anyway.fm/fonts/）
核对基准：源码 HEAD `eeb4259`，逐条查过实现位置，不凭印象
写作目的：每一项都回答四件事 —— 它是什么 / 为什么缺了会疼 / 现有底座在哪 / 怎么加、坑在哪

---

## 0. 总览

按「有没有底座」分三类，而不是按重要性分。有底座的改动成本通常只有新功能的 1/3。

| # | 缺口 | 类别 | 现有底座 | 面向用户的价值 |
|---|---|---|---|---|
| 1 | 缺字检测（预览文本级） | 有数据缺交互 | `health.rs` 字库级缺字 + `sweep_charset` 扫描 | 高 |
| 2 | 竖排预览 | 真缺 | 无（全部横排 div） | 高 |
| 3 | 叠层对比 | 半个 | `CompareOverlay.tsx` 并排 | 高 |
| 4 | 多版式自动样张 | 半个 | `specimen.ts` 单一版式 PNG | 中高 |
| 5 | 中文书体筛选 | 有数据缺入口 | `tagTaxonomy` + `tagSuggest` 规则 | 高 |
| 6 | 预览文本预设与历史 | 真缺 | `sampleText` 单值 | 中 |
| 7 | 行高调节 | 真缺 | 字号有 8 档滑杆 | 中 |
| 8 | OpenType 特性可视化 | 有数据无入口 | `get_features` 已返回数据 | 中 |
| 9 | 字符集标准判定 | 真缺 | `CjkStats` 只给总量与分区 | 高（国内刚需） |
| 10 | 字体指纹与来源可信 | 半个 | 详情页已有 SHA-256 | 中 |
| 11 | MCP / Skill 暴露给 Agent | 真缺 | 全部查询能力已在 Rust 侧 | 高（战略） |
| 12 | 次要缺口（排序/筛选/失败清单） | 零散 | 部分有枚举 | 低 |

## 1. 缺字检测（预览文本级）

### 它是什么

三件套，缺一件都不成立：

1. **标出**：列表行的预览文本里，当前字体没有的字单独染色（通常是红）+ 加下划线，并且用系统字体代显，让人看见"缺成了什么样"。
2. **计数**：行首一个徽章，`缺 4 个字符`；一个字不缺就显示 `这句不缺字`。
3. **筛选**：顶部一个开关 `只看不缺字`，一键把不能完整渲染当前文案的字体全筛掉。

### 为什么缺了会疼

挑字体时最贵的错误不是"不好看"，是"排版到一半发现缺字"。中文场景尤其致命：字体风格看着对，结果"喆""堃""昇"这类人名用字没有，等交付前才发现，整套稿子要换字。这个功能把"事后发现"变成"挑的时候就知道"，是 Anyway.Fonts 的第一卖点，也是它敢自称"更懂中文"的底气。

### 现有底座（比想象中多）

- `src-tauri/src/health.rs:174` `missing_common()`：已经有一份**现代汉语常用字表**，体检里会报"现代汉语常用字表中缺 N 字"（`health.rs:452-463`）。
- `lib.rs:649` `fonts_with_char` + `lib.rs:658` `sweep_charset`：按码点扫全库、多线程、按 CPU 核数切块，这套并发骨架可以直接复用。
- `lib/ipc.ts:606` `get_charset`：读某个 face 的完整码点表。
- 前端 `fontStore.ts:1420` `setCharFilter`：单字筛选的完整链路（输入 → 后端扫 → `charMatches` → 列表过滤）。
- `TopBar.tsx:333` 已有「包含此字符」输入框，UI 位置现成。

### 关键坑：`get_charset` 不能用来判缺字

`lib.rs:698` 的实现末尾有一行：

```rust
cps.sort_unstable();
cps.dedup();
cps.truncate(4096);   // ← 这里
```

4096 个码点是给字符地图用的（前端只画前几千个格子）。但中文字库动辄 2 万到 7 万码点，**被截断后的集合拿去判缺字会大面积误报**（排在 4096 之后的字全被当成"缺"）。所以不能走这条路。

正确做法是**按文本判定，不导出整个字符集**：文本通常几十个字，直接 `face.glyph_index(ch).is_some()` 逐字问，一次 `std::fs::read` + 一次 `Face::parse` 就够。

### 怎么加

后端新增一个命令（一次读文件，判整段文本）：

```rust
#[tauri::command]
async fn missing_chars(path: String, face_index: u32, text: String)
    -> Result<MissingReport, String>

// MissingReport { missing: Vec<char>, covered: usize, total: usize, has_glyph_but_blank: Vec<char> }
```

实现要点：

- 先对文本去重（同一段文案常重复用字），再逐字查 `glyph_index`。
- **`glyph_index` 返回 `Some(GlyphId(0))` 也算缺**——那是 .notdef，字体里有个空盒子。要判 `id != 0`。
- TTC 多 face：任一 face 覆盖即算覆盖（与 `sweep_charset` 的判定保持一致）。
- 跳过空白、控制字符；保留标点（标点恰恰是常缺的）。

前端：

- 新增 `lib/textCoverage.ts`：`useTextCoverage(sampleText)` 带缓存（key = `path|faceIndex|text`），文本变化时重新算，全库串行会卡，并发控制在 4。
- `FamilyCard.tsx` 渲染预览文本时按字符切分成 `<span>`，缺的字加 `className="glyph-missing"`。
- 徽章挂在 `FamilyCard` 的 meta 行；筛选开关加到 `TopBar` 的标签组旁边，`App.tsx:137` 的筛选依赖数组里加一个 `missingOnly`。

### 边界情况（不做会翻车）

| 情况 | 处理 |
|---|---|
| 组合字符 / ZWJ / emoji 序列 | 按字素簇（grapheme cluster）切，不按 UTF-16 码元；否则会把 👨‍👩‍👧 拆成三段报缺 |
| 变体选择符 U+FE0F | 不单独判缺，随基字判断 |
| 繁体/简体互转 | 不转。缺就是缺，"張" 缺不代表 "张" 缺 |
| 全角空格、NBSP | 不判缺，但要计入 total 时说明口径 |
| 性能 | 全库 500 个文件 × 每文件解析 ≈ 首次 1~3 秒；结果必须缓存，切视图不能重算 |

### 验收

- 拿一款确定缺字的字体（比如某些英文无衬线），输入含"喆堃昇"的文本，徽章应显示 `缺 3 个字符`，且这三个字在行内变色。
- 开「只看不缺字」，该字体从列表消失；关掉即回来。
- 切到瀑布流/列表视图，标红保持一致。

## 2. 竖排预览

### 它是什么

把预览文本按中文竖排规则渲染：字从上往下、行从右往左，标点落在字框右上/左下，西文与数字直立或整体旋转。

### 为什么缺了会疼

中文排版里有一整类需求是纯竖排的：书名、腰封、海报、古籍复刻、日式风格物料。横排看着没问题的字体，竖排可能暴露两个问题：纵向字面率不对（字显瘦）、标点位置错（句号压在字中间）。挑竖排用字时，横排预览基本没有参考价值。

### 现有底座

没有。`FamilyCard.tsx`、`FontList.tsx`、`WaterfallView.tsx`、`FontDetailView.tsx` 的预览都是普通横排 `<div>`，无 `writing-mode`。CSS 里搜不到一处 `vertical`（只有 `vertical-align` 和 `resize: vertical`）。

### 怎么加

纯前端，不需要 Rust：

```css
.vertical {
  writing-mode: vertical-rl;
  text-orientation: mixed;   /* 中文直立、西文按西文规则 */
  font-variant-east-asian: normal;
}
```

要点：

- **`text-orientation: mixed` 是默认值**，中文自动直立、拉丁字母整体旋转 90°；如果希望西文也直立（更像中文排版惯例），用 `upright`，但长英文会难读，建议做成可选项而不是默认。
- 竖排下「字号」= 字的高度、「行高」= 列与列的距离（`column-gap` 不起作用，靠 `line-height`）。所以行高滑杆在竖排模式下的语义要跟着改文案。
- 标点：浏览器会按 `vert`/`vrt2` 特性替换竖排标点，前提是字体里有这两个 GSUB 特性。字体没有时，句号会停在字框中间——这正是"用竖排能看出字体好坏"的原因，**不要替它修**，让它暴露出来才是价值。
- 详情页加一个 横排/竖排 分段控件（`fd-sample-tools` 里已有 `fd-size` 滑杆，并排放得下）；列表行建议不做竖排（行高会撑爆），只在详情页与对比视图开。

### 坑

- WebView2 是 Chromium 内核，`writing-mode: vertical-rl` 支持完好，但 `text-spacing-trim`（标点挤压）在旧版本不生效，别指望它自动收窄标点。
- 竖排 + `font-feature-settings` 同时开时，`vert` 与自定义特性会互相影响，测试时逐个开。
- 截图/导出样张时 canvas 不支持 `writing-mode`，要自己算坐标逐字画（见第 4 项）。

### 验收

- 详情页切竖排，「永夜一禅子，泠然心境中」应从上往下读、逗号在字框右上。
- 换一款无 `vert` 特性的字体，标点位置应明显不对——这是正确行为。

## 3. 叠层对比

### 它是什么

把两款（或多款）字体的同一个字叠在同一位置，半透明重合。骨架一致的地方颜色深，偏差的地方出现"重影"。配一个 X/Y 拖动对齐和「重置」。

### 为什么缺了会疼

并排对比只能看"整体气质"，看不出"横竖笔画的粗细比例差多少""重心高不高"。叠层是唯一能直观看出**同名字体是不是同一来源**（比如某商业字体和它的开源祖先）的方式，也是字体设计师判断"这套字能不能和那套字混排"的手段。

### 现有底座

`CompareOverlay.tsx`：

- 已经是多列并排（`--cols` 动态列数），每列渲染 hero `Aa` + 14/24/40 三档文案 + meta。
- 有加入/移出对比的完整链路，有 ESC 关闭、焦点陷阱。

缺的是**模式**：只有并排，没有逐行、没有叠加，也没有拖动对齐。

### 怎么加

不要另起一个弹窗，在 `CompareOverlay` 里加一个模式分段控件（并排 / 逐行 / 叠加），三种模式共用同一批家族列表。

叠加模式的实现：

```css
.overlay-stage { position: relative; height: 240px; }
.overlay-stage .layer {
  position: absolute; inset: 0;
  display: grid; place-items: center;
  font-size: 160px;
  mix-blend-mode: multiply;    /* 浅色主题 */
  opacity: var(--layer-opacity, .75);
}
[data-theme="dark"] .overlay-stage .layer { mix-blend-mode: screen; }
```

- 每层一个 `translate(var(--dx), var(--dy))`，拖拽用 pointer events 改这两个变量，`重置` 归零。
- 对齐基准：默认按 **baseline 对齐**（`display: flex; align-items: baseline`），因为不同字体 em 框与上伸部差别很大，按盒子居中会看起来"没对齐"。给一个 `居中 / 基线` 切换。
- 颜色建议：第 1 层纯黑、第 2 层纯红（或青），相乘后重合处近黑、偏差处发彩。这比"两个半透明灰"信息量大得多。
- 透明度滑杆 30%~100%，层数越多越要能调。

### 坑

- `mix-blend-mode` 在深色主题下必须换 `screen`，否则一片黑；这条容易漏，因为开发时大多在浅色下调。
- 拖动要限制在可视区内，否则拖出容器后用户找不回来，所以「重置」必须显眼。
- 三款以上叠加时颜色会糊，建议超过 3 款时提示"建议 2~3 款"。

### 验收

- 同一家族的 Regular 与 Bold 叠加，应看到笔画变粗、骨架不动的效果。
- 关掉一层，另一层不受影响；切并排模式，拖动位移不应污染并排布局。

## 4. 多版式自动样张

### 它是什么

不只看"这行字排出来什么样"，而是看"做成一张海报/一本书/一条诗签长什么样"。四套预设版式随机取内容：

| 版式 | 内容构成 | 用来看什么 |
|---|---|---|
| 海报标题 | 大字标题 + 英文小标 + 副信息 | 标题字的张力、字距 |
| 正文阅读 | 60~100 字现代文 + 页码 + 页眉 | 行气、灰度、可读性 |
| 竖排诗签 | 竖排短句 + 印章 + 编号 | 竖排节奏、留白 |
| 字形矩阵 | 同一个字排 4×5 矩阵，字号递减 | 同字在不同字号下的轮廓变化 |

每次「换一组」重新采样文案/日期/编号，版式不变。底部固定一行「自动生成，非厂商官方样张」。

### 为什么缺了会疼

单行预览能判断字好不好看，判断不了**排版好不好用**。正文用字真正的指标是灰度均匀、行距舒适，只有排成一段才看得出来。这也是对方把样张做成一等公民的原因——它直接对应"我要拿这个字体做什么"。

### 现有底座

`lib/specimen.ts`：能导出 PNG（宽 1100、`SCALE = 2`、内边距 72、瀑布 5 档 14/20/28/40/56、品牌行），内容取自 `detail.samples`（`font_detail.rs:434 build_samples` 按字体实际覆盖情况生成的样例行）+ 用户的 `sampleText`。

也就是说**能画一张固定版式的图，但只有一种版式，且只能导出、不能在界面里看**。

### 怎么加

新建 `components/SpecimenBoards.tsx`，四套模板，每套是一个纯函数 `(family, seed) => JSX`：

- 内容是常量池（文案 8~10 条、日期、编号、署名），用 seed 取模选，seed 存在 store 里，「换一组」= seed++。
- 渲染用 DOM（竖排模板才能用 `writing-mode`），不要用 canvas 画界面上的样张——canvas 画竖排要自己算每个字的坐标，成本高且难调。
- 导出仍走现有 canvas 链路：给 `specimen.ts` 加 `renderBoardPng(board, family, seed)`，一个版式一个绘制函数；竖排版式在 canvas 里逐字 `fillText`（x 固定、y 递增），标点位置按竖排规则偏移。
- 「自动生成，非厂商官方样张」这行必须印在图上，不只是界面上——否则样张流出去会被当成厂商物料。

### 坑

- `detail.samples` 是按字体覆盖生成的，西文字体和中文字体拿到的样例行完全不同；样张模板要能处理"没有中文样例行"的情况（回退到 ASCII 样张 + 提示）。
- 内容池里的字要和字体覆盖做交叉：**样张里出现缺字是最尴尬的 bug**。生成后跑一次第 1 项的 `missing_chars`，有缺字就换一条文案。
- 导出尺寸：1100 px 宽在 2 倍下是 2200，竖排诗签是竖构图，别强行套横版宽度。

### 验收

- 四套版式都能渲染，「换一组」四次内容应不同、版式不变。
- 竖排诗签里的标点位置正确，且字体缺字时不会出现豆腐块。

## 5. 中文书体筛选

### 它是什么

按**中文书体**筛：黑体、宋体、楷体、仿宋、圆体、隶书、篆书、行书、草书，与「衬线/无衬线」这种西式分类并列。

### 为什么缺了会疼

Fontora 现在唯一的分类是 `Classification = "serif" | "sans" | "mono" | "display" | "script" | "unknown"`（`lib/ipc.ts:5`）。这个分类对中文字体几乎失效：思源宋体、思源黑体、微软雅黑、苹方、方正楷体，全部落到 `serif` 或 `sans` 两个桶里。用户想"给我看所有楷体"，在现有筛选里做不到。

这是**买中文字体的人和做中文设计的人的第一筛选项**，对方把它放在左侧栏固定位置，不是没有原因。

### 现有底座（现成的，不用重新做词表）

- `lib/tagTaxonomy.ts`：0.9.0 刚建的「书体源流」组，13 个值就是 宋体/仿宋/黑体/楷体/圆体/隶书/篆书/行书/草书/西文衬线/西文无衬线/手写体/装饰体。
- `lib/tagSuggest.ts`：已经有一套从**族名关键词**推导书体的正则（`KAI_RE` / `SONG_RE` / `HEI_RE` / `仿宋|fangsong` / `圆|yuanti|round` / `隶|lishu` / `篆|zhuanshu|seal` / `行书|行楷|行` / `草|caoshu`），并且已经在详情页做「建议标签」。
- `tagTaxonomy.normalizeTag` 做归一化。

### 怎么加

不要新建一套并行的分类体系，**复用标签值，但提升为一级筛选器**：

1. store 加 `styleFilter: string[]`（书体值）与 `setStyleFilter`。
2. 判定顺序（重要，决定准确率）：
   - 用户手动打的标签（`tags[family]` 命中书体词表）→ 最高优先，且允许一个字体多书体。
   - `suggestFromDetail` 的推导结果（需要 detail 已加载，列表阶段可能没有）→ 次优先。
   - 族名规则（`tagSuggest` 里的正则，纯字符串，随时可算）→ 兜底。
3. UI：`TopBar` 的筛选菜单加一个「中文书体」分组，与「分类」并列；命中来源是推导的，chip 上加一个小圆点或 tooltip「自动判定」，并提供"以此为准"按钮写回手动标签。
4. 侧栏可加一行计数（黑体 12 / 宋体 28…），与现有标签计数复用同一套聚合。

### 坑

- **名字里没书体关键词的字体很多**：苹方、微软雅黑、思源黑体（黑体在名字里）、HarmonyOS Sans、MiSans、OPPO Sans——后几个既不含"黑"也不是 `sans` 以外的类型，只能靠"含汉字 + sans"推到黑体，会有误判。所以必须允许用户纠正，且纠正结果要沉淀为标签。
- 一个字体可能同时是"宋体"和"标题用"，书体是多值的，别做成单选。
- 日文汉字字体（明朝体/ゴシック）不要混进中文书体筛选，用 `scripts` 里是否含 Han + 语言判定挡掉。

### 验收

- 选「楷体」，列表只剩楷体类；思源黑体不出现在结果里。
- 手动把某字体标成「圆体」，它立刻出现在圆体筛选下，且标签页里能看到这个标签。

## 6. 预览文本预设与历史

### 它是什么

预览文本不再只有一个输入框，而是：

- **预设分组**：现代文 / 繁体 / 偏旁部首 / 基础笔画 / 常用标点 / 日文 / 韩文 / Lorem ipsum。
- **历史**：最近用过的 N 条文本，可点回填、可清空。

### 为什么缺了会疼

单个 `sampleText`（`fontStore.ts:381`，默认值来自 `t("preview.defaultSample")`）有个隐蔽问题：**一段文案看不出一款中文字库的全貌**。想验证偏旁部首是否齐全、标点是否居中、繁体是否支持、假名有没有，都得手动改输入框，改完前一组就丢了。挑字时这个动作一天要做几十次。

### 现有底座

`sampleText: string` 单值 + `TopBar.tsx:497` 一个 `topbar-sample` 输入框。预设在 i18n 里只有一条 `preview.defaultSample`。

### 怎么加

- 新建 `lib/samplePresets.ts`：`PRESET_GROUPS: { id, labelKey, items: {label, text}[] }[]`，每组 3~5 条，纯常量。
- 输入框右侧加一个下拉（复用现有 `ctx-menu` 或 popover 组件），分组标题 + 条目；点条目即 `setSampleText`。
- 历史：`sampleTextHistory: string[]`（上限 20），在 `setSampleText` 里 debounce 500ms 写入，去重、最新的在前；存进 `state.json` 的 prefs（`fontStore.ts:427` 已经在读 `prefs.sampleText`，同处加字段即可，无需迁移）。
- 每条预设旁标一行小字说明它用来看什么（"偏旁部首：看部件是否齐全"），否则用户不知道为什么要切。

### 坑

- 繁体预设要真的用繁体字，不要简繁混排——混排会让"缺字"结果失去意义。
- 日文/韩文预设只在字体 `scripts` 含 Hiragana/Katakana/Hangul 时才高亮推荐，否则一片豆腐块很劝退。
- 历史别存超大文本（>200 字截断），否则 `state.json` 会被撑大。

## 7. 行高调节

### 它是什么

预览区的行距倍数，1.0~2.0。作用于列表行、瀑布流、详情样张、竖排模式下的列距。

### 为什么缺了会疼

**字号已经有了**：`SIZES = [8,14,18,24,32,48,64,96]`（`fontStore.ts:34`）+ `TopBar.tsx:514` 的滑杆，详情页还有独立的 70%~160% 缩放（`FontDetailView.tsx` 第 508 行附近）。

缺的是行高。判断正文用字能不能用，看的是"一段排下来的灰度"，而灰度由字号与行距共同决定。只有字号没有行距，等于只能调一半参数。对方把行高单独做成 1.35 倍的控件，就是这个原因。

### 怎么加

- store 加 `lineHeight: number`（默认 1.4，范围 1.0~2.2），存 prefs。
- 三个渲染点各自读：`FamilyCard` 的预览 `<div style={{ lineHeight }}>`、瀑布流多行、详情 `fd-sample-text`。
- 竖排模式下同一个值映射到列距，`lineHeight` 仍生效（`writing-mode` 下行高就是列宽）。
- 顺手把字号滑杆从 8 档改成连续 px（8~96 步进 1），档位制在"想试试 22px"时会很难受——这是低成本高收益的顺手改动。

### 验收

- 拖行高滑杆，列表行高度、详情样张行距同步变化；切竖排后，列距跟着变。
- 重启软件后设置保留。

## 8. OpenType 特性可视化

### 它是什么

把字体支持的可选排版特性（连字、小型大写、旧式数字、分数、风格集等）逐项演示出来，开关式对比"开/关差别"。

### 为什么缺了会疼

字体的 OpenType 特性是**专业用户的分水岭**：做书籍排版的人会看 `onum`（旧式数字）和 `smcp`（小型大写），做品牌的人会看 `ss01`~`ss20`（风格集）。现在 Fontora 只能告诉你"有 8 个特性标签"，不告诉你长什么样——等于知道有钥匙但不知道开哪扇门。

### 现有底座

- `lib/ipc.ts:611` `get_features` 已经返回 `string[]`，`FontFaceDetail.features`。
- `lib/tagSuggest.ts` 已经在用 `features` 判"专业排版"标签（`smcp` / `onum` / `frac`）。
- 但 UI 层完全没有用：`FontDetailView.tsx` 里搜不到 `features`。

### 怎么加（这里有个关键简化）

**不需要自己解析 GSUB。** WebView2 是 Chromium，`font-feature-settings` 由浏览器排版引擎执行：

```css
.demo-on  { font-feature-settings: "smcp" 1, "onum" 1; }
.demo-off { font-feature-settings: normal; }
```

同一段文字渲染两遍，一遍开一遍关，并排放在一起就是最直观的演示。Rust 侧只要继续提供特性标签列表即可（`ttf-parser` 不解析替换规则，只给表存在性，这也说明"自己实现演示"本来就不现实）。

UI 结构：

- 详情页新加一节（现有 01~04 编号往后排），一行一个特性：左侧特性名 + 中文解释（`smcp = 小型大写`）、中间开/关示例（示例文字按特性选：数字特性用 `0123456789`，连字用 `ffi fl`，小型大写用 `AVATAR`）、右侧开关。
- 特性指南：一段说明 + 外链 W3C，避免用户不懂术语。
- 免责声明沿用对方的口径：上下文替换、定位特性、可变字体规则可能展不全；没有示例不代表没有这个功能。

### 坑

- 字体报有 `aalt` / `rlig` 这类特性但浏览器不直接暴露为 CSS 开关，演示会"没变化"——这类特性要标"需要排版软件触发"，不要给开关。
- `ss01`~`ss20` 数量不定，列表要动态；`cv01`~`cv99` 同理。
- 浅色/深色下示例的对比度，别用灰色文字演示。

### 验收

- 一款含 `smcp` 的字体，开/关两侧的 `AVATAR` 高度明显不同。
- 没有该特性的字体，不显示那一行（而不是显示开关但无效）。

## 9. 字符集标准判定（GB2312 / GBK / GB18030）

### 它是什么

直接回答"这款字体到底是不是 GB2312 / GBK / GB18030-2022"，而不只是"有多少汉字"。

### 为什么缺了会疼

这是评论区的原话：

> 可不可以实现一键识别字体标准啊，比如它到底是 gbk 还是 gb2312，亦或者 gb18030-2022

在国内，这是采购与交付的硬指标：政府/出版/教育项目招标文件里会写"字体须符合 GB18030"，排版交付要给甲方证明。用汉字总量猜是不行的——20902 个汉字不等于 GBK 合规，因为 GBK 是**特定字符映射表**，不是"汉字的数量"。

### 现有底座

`CjkStats`（`lib/ipc.ts:205`）：`totalChars / han / hanBasic / hanExtA...hanExtI / blocks`。它给你"汉字 20902 个、其中扩展 A 区 6 个"，但**没有任何一套标准的判定**。

### 怎么加

Rust 侧新增 `charset_standard.rs`：

1. 内置三张码表（离线打包，来源是 Unicode 官方映射文件）：
   - `GB2312.TXT` —— 6763 个汉字 + 682 个符号
   - `GBK.TXT` —— 20902 个汉字
   - `GB18030.TXT` —— 全量（含四字节区）
   这三份都是纯文本，压缩后几百 KB，塞进二进制没问题。
2. 与字体 cmap 求差（用 `cjk::face_codepoints`，注意它**没有** 4096 截断，这才是该用的那个函数）。
3. 输出结构化结论：

```rust
struct StandardReport {
    standard: "GB2312" | "GBK" | "GB18030",
    compliant: bool,
    covered: usize,
    total: usize,
    missing_sample: Vec<char>,   // 最多 20 个
}
```

判定优先级：GB18030 合规则 GBK、GB2312 必然合规（前者是后者的超集），所以从大到小判，报最高档。

UI：详情页规格表加一行「字符集标准」，显示 `GBK 合规（20902/20902）` 或 `GB2312 不合规，缺 132 字（例如 镕、燊…）`；再加一个筛选 `按字符集标准`。

### 坑

- **GB18030 有三个实现级别**（1 级 = 全部 Unicode 字符，2 级 = 常用，3 级 = 特定领域），2022 版还有强制实现级别要求。不要笼统说"支持 GB18030"，要标明是"覆盖 GB18030 双字节区 + 四字节区抽样"。
- GBK 的 20902 是"字符数"，含非汉字（符号、假名、希腊字母），只数汉字会得出错误结论。
- 字体可能通过 `cmap` format 4 之外的子表覆盖，取并集再判。
- 报"不合规"时一定要给缺字样本，否则用户无法判断是"真的缺"还是"判错了"。

### 验收

- 思源黑体应报 GB18030 双字节区合规；一款只做常用 3500 字的字体应报 GB2312 不合规并给出具体缺字。

## 10. 字体指纹与来源可信

### 它是什么

入库时给每个字体文件记一次 SHA-256，之后每次扫描比对；文件变了就告警。再叠加"来源"（官网/客户给/网盘）与"授权"（可商用/仅个人）两个用户可填字段。导出字体包时带一份指纹清单。

### 为什么缺了会疼

评论区的担心很具体：

> 要是能解决版权问题就好了，从网上下的免费商用我不敢用，因为我怕暗改

"免费商用字体"最大的风险不是授权条款，是**来源不明导致的版本被替换**：有人把开源字体改两笔、改个名、声称是另一款。这类问题靠人工比对不可能发现，靠哈希是几分钟的事。

### 现有底座

详情页已在算并展示 SHA-256（规格表里的那一行）。缺的是"记住"和"比对"。

### 怎么加

- `cache.db` 里给 `faces` 表加 `sha256`、`first_seen_at`、`trust_state`（`unknown / verified / changed`）。DB 版本号升一级，写迁移。
- 扫描时：文件大小 + mtime 都没变就跳过哈希（性能）；变了就算新哈希，与库里的比：
  - 一致 → `verified`
  - 不一致 → `changed`，在列表和详情都挂一个警示徽章，并记录"原哈希 / 现哈希 / 发现时间"
  - 库里没有 → `unknown`，首次记录
- 用户可手动"信任当前版本"，把 `changed` 重置为 `verified` 并留一条日志（`Data\` 里已有操作日志机制）。
- 导出清单（`export.rs` 已有清单导出）加一列哈希，交付方拿到 Fontora 就能校验。
- **不做联网校验**，离线是本软件的底线；要对比"官方版本"就让用户自己导入一份参照文件。

### 验收

- 手动改一个已入库字体文件的末尾一个字节，重新扫描后该字体出现"文件已变更"徽章。
- 导出清单里含 SHA-256，且与详情页一致。

## 11. MCP / Skill：把字体库暴露给 Agent

### 它是什么

把 Fontora 的字体库变成 Agent 能调用的工具集。Agent 在设计/写代码时可以直接问："我库里有哪些适合做民国海报的宋体""帮我找支持 GB18030、带旧式数字的衬线体，排一版竖排小样"。

### 为什么这件事对你特别值

这是评论区最高赞的建议（6 赞），而且作者本人回复"已添加初版"——**对方已经在做了**。但这件事上你有结构性优势：

- 它是网页工具，Agent 拿不到你的本地库、本地标签、本地文件路径。
- 你的查询能力已经在 Rust 里齐了：`db.rs`（索引）、`store.rs`（标签/集合/收藏）、`font_detail.rs`（规格/覆盖/许可）、`export.rs`（渲染）、`health.rs`（体检）。
- 你的标签体系（0.9.0）正好是 Agent 最需要的语义层——"宋体 + 品牌海报 + 大字库"这种查询，纯靠文件名做不到。

### 怎么加

独立 bin，别塞进 GUI 进程：

```
src-tauri/src/bin/fontora-mcp.rs   →  stdio JSON-RPC 2.0
```

- 协议：MCP 的 `initialize` / `tools/list` / `tools/call` 三个方法就够起步。
- 工具集（第一版 6 个）：

| 工具 | 入参 | 返回 | 复用 |
|---|---|---|---|
| `list_fonts` | 书体/标签/安装状态/字符集标准 | 家族列表 + 简要指标 | `db.rs` 查询 |
| `search_fonts` | query | 命中家族 + 命中原因 | 现有搜索（拼音/别名） |
| `font_detail` | family | 规格、许可 fsType 解读、覆盖 | `font_detail.rs` |
| `missing_glyphs` | family, text | 缺字列表 | 第 1 项的新命令 |
| `render_sample` | family, text, size, vertical | PNG（base64 或临时路径） | `fontdue`/`ab_glyph` 栅格 |
| `suggest_by_tags` | 标签组合, limit | 排名后的家族 | `store.rs` 标签 |

- 数据一致性：MCP 进程只读 `cache.db`（SQLite 支持多读），**不写** `state.json`；写操作（打标签、收藏）暂不暴露，避免与 GUI 抢锁。

### 坑

- 用户可能从没打开过 GUI，`cache.db` 不存在——MCP 启动时要能自己触发一次扫描，或用空库正常返回而不是崩。
- 路径要绝对路径（Agent 拿不到相对路径的上下文）。
- 别把整个 `state.json`（含所有标签/备注）一次性返回给模型，按需查询；否则 token 爆炸还泄露隐私内容。
- 渲染 PNG 要控制尺寸（≤1024px），否则 base64 太大。

### 验收

- 在 Claude Code / WorkBuddy 里挂上这个 server，问"我库里有哪些楷体，哪些支持繁体"，能返回真实家族名。
- GUI 关闭时 MCP 也能工作（只读库）。

## 13. 依赖关系与建议顺序

几项之间有共享底座，一起做能省一大截：

```
第 1 项 缺字检测 ──┬── 第 9 项 字符集标准（同一套 cmap 判定）
                  ├── 第 4 项 样张（生成后验缺字，防豆腐块）
                  └── 第 11 项 MCP 的 missing_glyphs 工具

第 2 项 竖排预览 ──── 第 4 项的竖排诗签模板

第 3 项 叠层对比 ──── 需要重构 CompareOverlay 的模式层（一次做掉并排/逐行/叠加）

第 5 项 书体筛选 ──── 复用 0.9.0 的 tagTaxonomy + tagSuggest（零新词表）
```

推荐的落地顺序（按"底座复用率 × 用户可见度"排）：

1. **第 1 项**：一个命令 + 三个 UI 点，直接吃到 `sweep_charset` 的并发骨架。
2. **第 5 项**：几乎零后端成本，直接提升中文筛选命中率。
3. **第 2 + 4 项**一起做：竖排是样张的竖排版式的前置。
4. **第 3 项**：把对比视图的模式层一次重构到位。
5. **第 9 项**：接在第 1 项后面做，共用码表与判定。
6. **第 11 项**：前面几项做完，MCP 要暴露的能力就都齐了。
7. **第 6 / 7 / 8 / 10 / 12 项**：随时插空做，互不依赖。

## 14. 一个提醒

上面 11 项里，有 4 项（缺字、书体、OpenType、字符集标准）都是"**数据已经在，只是没有出口**"。这类缺口的性价比远高于从头做新功能，但也最容易反复出现——因为功能做了一半（后端返回了数据）就提交了。

0.9.0 那次发版事故（功能做完没打包）和这批"有数据没界面"是同一个毛病的两种形态：**完成度是按"代码能跑"算的，不是按"用户能看见"算的**。建议以后每个功能 commit 的验收条件里明确写一句"用户在哪里点得到它"。
