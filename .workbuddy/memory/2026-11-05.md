## 第五轮：空白卡片与卡片密度（21:20，Fontora 0.10.5）

用户截图报了三个问题：卡片「被切得太碎」、超世纪那几只「无法预览」、白舟一整片「啥也没有」。
三件事其实是三个独立原因：

1. 「这种格式暂时无法预览」= OTS 拒收字体，不是 WebView 的锅。
   用 Chrome headless 加载直接拿到原因：`OTS parsing error: cmap: misaligned table`。
   全库扫了一遍（表目录 offset % 4），只有 18 个文件有病：超世纪 4、经典 3、
   超研泽中黑体 1、魂心 1、Ruach LET 1、TrueLogo 系列 8。
   修法两层：先重排表目录（必须按 tag 升序，否则换一条 `Table directory is not
   correctly ordered`），再按原映射重写一张干净的 cmap 格式 4（原表长度字段少算了
   末尾 glyphIdArray，报 `bad glyph id offset (41804 > 41804)`）。
   修完 18/18 全部加载成功，除 head 与 cmap 外逐表字节一致，glyf 哈希相同。
   备份放在 `G:\Mine\素材类\字库_字体修复备份_20261105\` —— 备份不能放在字库目录
   里面，否则会被 Fontora 当成重复字体再索引一遍（第一版放在
   `字库/字库整理报告/` 下，scan.log 立刻多出 18 个 parsed）。

2. 白舟/★日文毛笔那种「白板」= 字体把 ASCII 挂成空字形：cmap 查得到 gid、字体
   加载成功、`document.fonts.check` 也是 true，但 glyf 里 loca[g]==loca[g+1]，
   画出来什么都没有。覆盖率检测抓不到这种情况，只能实画一遍数像素
   （canvas fillText + getImageData 扫 alpha）。
   踩坑：canvas 里字体没被真正用过时不会去加载，探测会落到回退字体、恒为 true；
   必须先 `document.fonts.load()` 再探。落地成 `useInkOk()`：无墨 → 改用字体名
   （这类字体名字里的汉字基本都有墨），连名字都空 → 写明「没有可显示的字形」。

3. 「切得太碎」= 每张卡自带 12px/32px 深投影 + 20/22 内边距，一行文字被裹成一个
   浮起来的方块。去掉投影（只留 1px 落地感）、内边距压到 12/18、示例与标题间距
   16→8、行距 18→10，同样高度多看约 1/3 行。
